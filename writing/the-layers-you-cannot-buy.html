The layers you cannot buy.

Enterprise agents stall between pilot and production, and the model is rarely why. The stack has split into layers you can rent and layers no vendor can decide for you. A map of both, a five-part test for whether an agent is ready, and the order to build a platform in.

Gagan Sachdeva · 12 October 2026 · ~32 min read · Agentic AI strategy · Platform engineering

Every agent tutorial starts the same way. Paste your API key here.

No enterprise I know builds like that. In a regulated company the first model call goes to reserved capacity on Azure, a Bedrock endpoint pinned to an approved region, or an open-weight model on the company’s own GPUs, each one signed off by procurement, security and risk. It passes through a gateway that checks who is calling and counts every token. Then the agent tries to reach the system that actually holds the work, and finds it has no API. It is a twenty-year-old application with a green screen, a nightly batch file and three people who know how it behaves.

Most enterprise agent programmes stall in the gap between the tutorial and the building, and rarely because of the model.

The gap is narrowing, unevenly. Some layers of the stack became close to solved in the past year, and you can adopt them and move on. Others are still open, and no vendor will close them for you, because what is missing is a set of decisions only your organisation can make.

This essay is a map of which is which, the test I use to tell whether an agent is ready to act, and the order I would build in if I were starting an enterprise AI platform from nothing tomorrow.

A note on examples: the products named here are ones practitioners discuss in public, and the build is described in industry-general terms. Nothing here describes any institution I have worked with.

The argument in 60 seconds

Enterprise agents fail on the layers around the model, and those layers have split in two. Execution, context management, tool connectivity and trace tooling are maturing fast: adopt them. Identity, authority, memory, transparency, evaluation content and ownership are still open, because what they need is decisions, not software. The working rule is to adopt the mechanism and design the content. One test, CLEAR, tells you whether the content is there: does the agent understand the job, what may it do, can we prove it worked, who owns the outcome, and what does it return after full cost. Start below the tutorials, with how your enterprise actually reaches a model and with the systems that have no API. Give every agent an identity, an owner and written authority before it goes live, and let a gateway enforce trust on every hop: agent to model, agent to tool, agent to agent. Treat memory as a governed record, not a cache. Make what agents do visible to the people they work alongside. Then build in phases, each with an exit gate, and judge the platform by one number: whether the second team ships faster than the first.

01 · SignalAdopt the mechanism, design the content

Read the practitioner forums, GitHub issues and engineering write-ups, and look only at what teams complain about once an agent leaves the demo. The complaints sort into two piles.

The first pile is engineering problems that tools are now solving. Agents that crash halfway through a long task. Retries that repeat an action. Context windows that bloat until the agent is slower, dearer and less accurate at once. Wiring an agent to a tool. Capturing traces and running evaluations. A year ago each of these was a custom build. Today each has credible products, open-source options or managed cloud services.

The second pile is decisions that no tool can make for you. Which agents exist, who owns each one, and on whose authority it acts. What an agent may never do, however persuasive the context. What it should remember, and for how long. What good looks like for this task in this organisation. Who can see what the agent did. How to reach the systems with no API. Who answers when it goes wrong. Vendors sell mechanisms for all of these. None of them can sell the content.

Adopt the mechanism. Design the content.

Several layers split down the middle. Evaluation is the clearest case: the harness that runs tests and stores traces is maturing fast, but the test set, the grading criteria and the release threshold are yours, and they decide whether the agent is any good. Identity is another. The products that issue agent identities now exist. The decision about what each agent may decide does not come in the box.

02The test: CLEAR

Every readiness review I have sat through started as an argument about the model and ended with nobody able to say whether the agent could be trusted. So I wrote down the five questions that actually decide it, and I have used them since in every review and in the talks I give on this. The initials spell CLEAR.

LetterThe questionWhat answers itWho supplies the answer
ContextDoes the agent understand the job? Not the task description: this client, this case, the policy that applies, what has already been tried.Memory and knowledge, the integration ladderDomain owners and knowledge stewards
LimitsWhat may it do, what may it never do, and are those limits enforced somewhere a prompt cannot reach?Identity, authority, invariants at the tool layerThe agent’s owner, security and risk

Hold the map in Figure 1 against the test and the split explains itself. The maturing layers make Evidence cheaper to collect and Limits cheaper to enforce. They cannot answer a single question on their own, because every answer is content: your clients, your limits, your definition of good, your named owner, your cost. That is why an agent built on the best managed runtime in the market can still fail CLEAR on all five, and why the rest of this essay is organised around supplying those answers.

03Layer zero: how enterprises actually reach a model

Tutorials skip this layer because it does not exist for a developer with a credit card. In an enterprise it is the first thing you build, and it shapes everything after it.

Enterprises reach models in three ways, and almost never through a raw vendor key. Managed model services inside a cloud they already have a contract with: Azure OpenAI and the wider model catalogue in Microsoft Foundry, Amazon Bedrock, Google’s Vertex AI. These come with private networking, the company’s existing identity provider, regional data residency and an enterprise agreement that procurement has already negotiated. Reserved capacity on those services, such as Azure’s Provisioned Throughput Units (PTUs) or Bedrock’s provisioned throughput, for workloads that need predictable latency. And self-hosted open-weight models on the organisation’s own GPUs, where residency, sovereignty or volume justifies it.

Capacity is a planning problem, not a payment method. A PTU is a slice of dedicated throughput, billed by the hour whether you use it or not. It comes in Global, Data Zone and Regional deployment types, and a reservation for one does not cover another. Quota is not capacity. When reserved capacity is fully used, requests start failing with rate-limit errors unless you have configured spillover to a standard pay-as-you-go deployment. The common pattern is to reserve for steady load and spill the peaks. Microsoft’s own advice is to size by benchmarking on your own data, and that matters more for agents than for chat, because an agent resends its growing history on every turn. Size from agent traces, not from last year’s chatbot traffic.

Residency narrows the menu. Regulated workloads often need regional deployments, which tend to be the most expensive tier, and new models usually reach a given region later than they reach global endpoints. So never let an agent assume a particular model. The model under it will change more often than the agent does.

The AI gateway comes before the first agent. Put one control point between every agent and every model endpoint. It checks the caller’s identity, enforces token limits per agent and per team, applies content safety, routes between reserved capacity, spillover and alternative providers, attributes cost to the agent that spent it, and logs what happened without storing bodies where privacy forbids it. It is also where you swap models without touching a single agent. The vendors have reached the same conclusion: Microsoft now requires an AI gateway before some of Foundry’s governance features become available, including token quotas, custom agent registration and MCP tool governance.

Self-hosting earns its place when no managed model is available in the region you need, when volume is high and steady enough to beat reserved pricing, or when a small fine-tuned model can take a narrow, high-volume task off a frontier model. Put it behind the same gateway. Agents should never know, or care, where the model they are calling runs.

04The legacy reality: when there is no API

The second thing tutorials assume is that the work lives behind a clean API. In most large enterprises a meaningful share of it does not. It lives in core systems built decades ago, in vendor packages whose integration layer was never licensed, in applications that expose a screen and a nightly file and nothing else.

The instinct is to let the agent figure it out: give it a browser, point it at the screen, let computer use do the rest. Computer use is now fast enough to tempt you; on some tasks it beats a person. But a screen built for people is the most fragile interface an enterprise owns. It changes without notice, it has no idempotency, and an agent that misreads it can do real damage quickly.

The better approach is a ladder. Start at the highest rung that exists for a given system, and treat every step down as a cost you are choosing to pay.

  1. A real API exists. Expose it as a tool, typically an MCP server, behind your API management layer, so every call carries an identity, a scope and a log. Expose a handful of business actions, not every endpoint. Agents choose tools worse as the list grows, and every tool definition costs tokens on every call.
  2. An API exists, but in the wrong shape. Chatty, internal-only, built for another application rather than for a machine acting on a person’s behalf. Build a thin facade that performs one business action end to end, and let the agent call the facade.
  3. No API, but the data is reachable. Read from a replica, the data platform or an event stream. Send writes through a channel the system already trusts: a queue, a file drop, an existing workflow. Keep read paths and write paths deliberately separate.
  4. Only a screen. Now computer use or robotic process automation is justified, as a last resort. Script the deterministic steps, keep the model for the parts that need judgement, run each session under its own identity in an isolated environment, and log every action.
  5. Nothing at all. A person does it. The agent prepares the case and the person executes. Capture what they did as structured data, so that one day you can climb a rung.

Two principles sit under the ladder. First, the agent should never be the integration layer. The model decides what should happen; deterministic code makes it happen. Second, authentication has two hops. The agent proves who it is to the tool, and the tool then has to act on the downstream system on behalf of a specific person. The protocol covers the first hop well and the second hardly at all, which is why practitioners keep describing remote MCP in production as an authentication problem first.

05The maturing layers: adopt, don’t build

The managed runtimes are the biggest change of the past year, and for a team starting from scratch they are the obvious default. None of them will tell you what your agents should be allowed to do. That is where the rest of this essay goes.

One caveat on tooling. I have argued for trace-first agent systems and built my own harnesses. That is consistent with adopting the tooling here: build your own only where the trace format or the approval gates are the thing you need to own.

06Identity, authority and how agents trust each other

Of the open layers, this is the one I would design first, because every other control depends on it. You cannot scope a memory, enforce an approval or read a trace if you do not know which agent acted and for whom.

The problem

Few enterprises can produce a complete list of their agents. Orchid Security estimates that roughly half of enterprise identity activity already happens outside central identity management. A security vendor writing in The Hacker News described a global finance company that found three times more AI tools running than IT had approved. Many agents arrive without anyone deciding: they ship inside software the company already runs, through a product update, and inherit that product’s permissions. And where agents talk to each other, the API key the tutorials started with comes back in through the side door: a 2026 Zenity report found that 45.6% of enterprises authenticate agent-to-agent calls with shared keys. Nobody can then say which agent did what.

Identity: a registry, and a name for every agent

Agent identity is now a product category, and it matured faster than most people noticed. On a Microsoft estate, Agent 365 is now the single inventory for agents from Microsoft, partners and custom builds, and Microsoft Entra Agent ID remains the identity underneath it. Each agent gets its own identity, with owners and sponsors, conditional access and lifecycle controls applied to it as they are to a person. Unmanaged agents can be discovered, and an agent can be paused or switched off from one console. AWS has an equivalent in AgentCore Identity, which gives each agent a distinct identity and works with existing identity providers such as Entra ID and Okta.

What the products do not give you is the content. Every agent still needs a named owner who answers for it, a stated purpose, a list of the tools and data it may touch, an autonomy level and a review date. Write those down before the agent exists. It is never easier than then.

Authority: what an agent may decide

Identity says who the agent is. Authority says what it may decide: which decisions, up to what limit, whether the action can be undone, and who it escalates to. In The Levels of an AI-Pilled Organization I argued that authority should follow reversibility rather than rank. With agents it stops being theory: no manager sits in the path to catch an irreversible call. Record authority in the registry, in a form a machine can check, and enforce it outside the model.

Enforcement: a gateway on every hop

An agent has three kinds of conversation, and each needs the same treatment. It talks to models, to tools and to other agents. The cleanest designs put one enforcement point in front of all three. Gravitee’s AI gateway, released in June, is one example: a single runtime for model, MCP and agent-to-agent traffic, sharing authentication, policy and tracing. Its agent-to-agent proxy reads what another agent can do from its published agent card, authorises each skill separately and verifies the calling agent’s identity. Its access management registers agents as OAuth clients, from desktop assistants to hosted services and background workloads. Azure API Management and AgentCore Gateway play similar roles on their own clouds.

The product matters less than the rule: no agent reaches anything except through a point that checks who it is, what it may do, and writes it down.

How agents trust each other inside the organisation

Follow one delegation. A person asks an orchestrating agent to prepare a credit review. The orchestrator hands part of the work to a specialist agent, which needs a document from a system of record. Three hops, three rules.

  • The person signs in and the orchestrator acts on their behalf, with a delegated token carrying only that person’s rights. No agent holds standing access to anything it could reach on its own.
  • When the orchestrator calls the specialist, the token is exchanged rather than passed on. The new token names both agents and the original person, and its scope can only shrink. A specialist never holds more rights than the person it ultimately works for, or than the agent that called it.
  • When the specialist calls the system, it receives a token for that one system and that one purpose, still on the person’s behalf. One trace identifier follows the case through all three hops.

The test of this design is the single question an auditor will ask: on whose authority did this happen? With exchanged tokens and one trace, the answer is a lookup. With shared keys, it is a guess.

Who issues the tokens, and who checks them

The question I am asked most about Figure 2 is who actually does the authentication as a token moves from person to agent to agent to system. It is not the gateway, or not only the gateway. Four parties take part, and each has one job.

  • The identity provider issues, and only the identity provider. Entra ID, Okta or Ping, or on AWS the provider behind AgentCore Identity. It issues the person’s token at sign-in and performs every exchange along the chain: when the gateway needs a narrower token for the specialist, it asks the identity provider, which consults the registry’s record of what that agent may hold before it answers. The standard mechanism is OAuth 2.0 token exchange; Entra’s on-behalf-of flow is one implementation of it. No gateway, agent or tool mints authority of its own.
  • The agent proves who it is before it may ask for anything. It does so with a workload identity: a managed identity on Azure, an IAM role on AWS, a SPIFFE identity on Kubernetes, or a client certificate. Never a secret in a configuration file. This is what makes “one identity per agent” real: the identity provider knows the agent as a principal it can revoke.
  • The gateway checks, enforces and records; it does not decide. It validates the signature, audience, expiry and scope of every token that passes, applies the policy the registry holds, requests the exchange, and writes the trace. Gravitee’s access management, Azure API Management and AgentCore Gateway each do this; Gravitee’s can also act as the authorisation server itself for estates that want one product in both roles.
  • The receiver checks again. The specialist agent, the MCP server and the system of record each validate the token they are handed against the identity provider’s keys and refuse anything with the wrong audience. A tool that trusts the gateway blindly is a tool with no front door.

Short lifetimes close the loop. Tokens live for minutes, not days, so pausing an agent in the registry stops it at its next exchange. Issued by the identity provider, held briefly by the agent, checked at the gateway and again at the door, revoked from the registry. Four parties, one source of authority.

When the other agent is outside

Agents will increasingly deal with agents that belong to someone else: a supplier’s, a counterparty’s, a customer’s own assistant. Treat every external agent as a third party, the way you would treat a vendor’s system. Allow-list the agents you will talk to and verify their identity with mutual TLS or signed credentials. Never let an internal token cross the boundary; exchange it at the edge for one scoped to that partner and that purpose, and share only the data the task needs. The platforms have started to enforce this for you. Microsoft’s agent service refuses to pass a Microsoft-issued token to an untrusted tool endpoint.

The agents you did not build

The hardest agents to govern are the ones inside software you already own, and the assistants employees build for themselves in low-code tools. Bring them into the same registry, under the same rules. An inherited agent whose only governance is a chat tool’s channel membership is an autonomous actor with no owner.

07Memory: what agents remember, and who decides

Memory is where the gap between demo and enterprise is widest, and where the products are least mature. In a demo, memory is a feature. An enterprise agent that remembers the wrong thing, for the wrong person, for too long, is a data incident.

Four kinds of memory, four sets of rules

It helps to stop saying “memory” and name what is being remembered.

KindWhat it holdsScopeLifetimeWho may write
Working contextWhat the agent needs for this task, right nowOne runDiscarded at the endThe agent, through the gate’s lightest checks

Most memory incidents come from mixing these up: a working note promoted into shared knowledge without review, or case memory from one client surfacing in another client’s session.

The write gate

The research on agent memory security has converged on one principle: treat every write to memory as a privileged change, not a side effect. Before anything is committed, check where it came from, whether it contradicts or supersedes something already held, whose memory it belongs to, and how sensitive it is. Filters at retrieval time are not enough, because poisoned entries usually look harmless on their own. The PoisonedRAG study showed that five planted documents in a corpus of millions could steer targeted answers about 90% of the time.

Scope, staleness and forgetting

  • Scope retrieval to the person and the purpose. Data retrieved in a privileged session must not surface later for someone without the right to see it. Keep memory separate per person and per case, and check content-level permissions again at retrieval.
  • Give knowledge a shelf life. Memory stores do not know that last week’s note supersedes last year’s. In The Search Tax I found that a half-built knowledge layer can be worse than none, because confident staleness makes agents stop early and act on the old answer. Supersession and expiry need an owner.
  • Make forgetting provable. Privacy law requires that personal data can be deleted on request, and few memory stores can yet prove a deletion. Keep the audit log, operational memory and user-deletable memory apart, so that deleting from one does not destroy evidence held in another, and verify each deletion afterwards.

The most valuable memory is also the hardest to capture: the reason an expert overrode the agent. That is the Amnesia Tax in engineering form. Rent the memory store. Own what goes into it.

08Transparency: who can see what the agents are doing

An organisation that cannot see its agents cannot trust them, and people route around what they do not trust. Transparency is usually discussed as a regulatory duty. Inside the organisation it is a condition for adoption.

There are four audiences, and each needs something different.

  • The people who work alongside agents. They should be able to look up every agent in the organisation: what it does, who owns it, what data it touches and how well it is performing. A registry that only administrators can read is an inventory. A registry that staff can read is a contract.
  • The people agents act on. Customers, counterparties and employees affected by an agent’s work should know when they are dealing with one. In the EU this now applies: the AI Act’s Article 50 transparency obligations, including telling people when they are interacting with an AI system, have applied since 2 August 2026.
  • The people who check the work. Auditors, risk teams and supervisors need decision records: what the agent was given, what it consulted, what it did, on whose authority, and what a person approved. The EU’s logging obligations for high-risk systems were pushed back by this year’s Digital Omnibus, to December 2027 for most high-risk uses and August 2028 for AI built into regulated products. Build the logging anyway. The trace you need for debugging is the same record a supervisor will ask for.
  • The agents’ own record. Publish each agent’s scorecard internally: volumes, error rates, escalations, incidents and what changed after each one. An agent whose mistakes are visible gets corrected. One whose mistakes are hidden gets switched off quietly, or not at all.

Two design choices make this work. Label agent actions where they land. When an agent writes to a system of record, the record should say so, and say on whose behalf. And capture the work, not the worker. Record decisions and their reasons at the point of work, with purpose limits people can see. If transparency feels like surveillance, people move their real work into side channels, and the record fills up with the official story.

09Evals: what the traces are for

Every agent platform now collects traces: each run broken into spans, one for every model call, tool call and handoff. That part is plumbing, and section 05 says to adopt it. The questions that matter come after the trace is stored. What happened in this run? Was it right? Would we know if the agent started to go wrong? And could we show a supervisor the answer?

Read the trace as a case, not as spans

A span tells you a tool was called, how long it took and whether it returned an error. A reviewer needs something else: what the agent was asked, what it consulted, what it decided, on whose authority, and what happened next. So the first job is translation. Turn each trace into a case record written in the language of the business. The same record then serves the engineer who debugs it, the expert who grades it and the auditor who checks it.

Grade three things, not one

  • Outcome. Was the answer or the action right? Most evals check only this, and it is the least informative of the three.
  • Path. Did the agent consult the right sources, call the right tools in a sensible order, and stop when it should have? A right answer reached the wrong way is luck, and luck does not repeat.
  • Policy. Did it stay inside its limits: no action without the approval it needed, no data it was not entitled to see, no invariant bent? One policy failure outweighs a hundred good outcomes.

Engineers can automate the checking. Only people who know the work can say what “right” means, so domain experts write the grading criteria and grade the hard cases. It pays: Forrester data reported by AI News put the rollback rate for agents without automated evals at 47%, against 9% for agents with full coverage.

Close the loop

The trace is the raw material, not the product. Each graded case joins the eval set. The eval set gates every release, including a quiet model swap at the gateway. The same grading runs on a sample of live traffic. And every incident becomes a new case, so the same failure cannot ship twice. Agents are not deterministic, so judge them on rates across many runs, never on one run passing.

Where model risk management comes in

Banks already have a discipline for this. Model risk management grew up around credit scores and pricing models, and supervisors have written it down: the US Federal Reserve and OCC in SR 11-7 in 2011, the UK’s Prudential Regulation Authority in SS1/23, in force since May 2024, and in the UAE the Central Bank’s Model Management Standards and Guidance, issued in December 2022 for every bank operating in the country. None was written for agents. All are written broadly enough that supervisors will apply them to anything that turns data into decisions.

The useful discovery is that the loop above already is model risk management, in a new form.

What model risk asks forWhat it means for an agentWhere the evidence comes from
Inventory and tieringEvery agent registered and tiered by the impact of its decisions and how much it may do aloneThe agent registry
Validation before useThe agent passes its eval set before release; for higher tiers, someone independent of the builders reviews the set and the resultsEval set and release gate

Ongoing monitoringGraded live samples, with alerts on drift and on any policy breachMonitoring
Explainability and auditAny single decision can be reconstructed: inputs, sources, actions, authorityCase records

Two things are new, and both are worth raising with your risk team early. First, the unit of validation is the agent, not the model. The same model behaves differently with different tools, prompts and limits, and the model underneath will change while the agent does not. Validate the whole system, and treat a model swap as a change that must pass the gate. Second, the evidence is statistical. An agent can answer the same case two ways, so validation means pass rates over enough cases, with policy checks held to zero tolerance.

A supervisor asks four things: show me what the system did, show me it was tested, show me someone independent challenged it, and tell me how you would know if it drifted.

Traces answer the first question only after someone turns them into cases. Evals answer the second and the fourth. Model risk management answers the third. Build the three together and the supervisor’s visit becomes a demonstration rather than an investigation.

10The rest of the open layers

The security boundary

Indirect prompt injection is still under-modelled, though it is often the bigger enterprise risk. In one reported case a developer asked a coding agent to check a fix to an internal billing screen, and the agent published the screenshots to a public repository in his personal account. Gravitee’s 2026 survey found that 54% of organisations had experienced or suspected an agent-related security or privacy incident in the past year.

Assume the model will be manipulated, and treat it the way you treat an insider with broad access: useful, and never the last line of defence. Put the controls outside the model. Separate agents that read from agents that act. Allow outbound traffic only to approved destinations. Keep credentials out of the model’s context entirely and broker tokens per call. Require human approval for anything irreversible. And enforce the rules that must never bend, such as limits, holds, deadlines and purpose restrictions, in code at the tool layer. A prompt can be argued with. A constraint in the execution path cannot.

Ownership and operations

The pilot is owned by an innovation team. Production needs someone accountable when the agent makes a wrong call at two in the morning, and Gravitee’s survey found only about one organisation in five fully secures its agents in production.

Gate every agent into production with named owners and recorded evidence, and re-certify it whenever the model changes, a tool changes, behaviour drifts or an incident occurs. Test the rollback and the kill switch before you need them. In regulated industries, map agents onto the risk tiering your model risk function already runs rather than inventing a parallel process; the higher the tier, the more independent the validation. And treat traces as evidence from day one, because sooner or later someone will ask for them.

11 · ActionBuilding an AI platform from scratch

Here is how I would build an enterprise AI platform if I were starting tomorrow with nothing but a cloud contract and a list of use cases. It runs in phases, each with an exit gate drawn from CLEAR, because the usual failure is sequence: a polished agent with no identity, or a platform with no flow running on it.

First, the shape you are building towards.

Phase 0 · Decide before you build

Four decisions shape everything after them, and none of them is an engineering task.

  1. Your model access posture. Which managed services, which regions, what residency your regulators expect, and whether any workload justifies self-hosting.
  2. Your risk tiers. In regulated industries, agents should sit inside the model risk framework you already run, not beside it. Agree with risk which tiers exist, what evidence each one needs and who validates the higher tiers. Doing this first turns risk into a co-designer instead of a gate at the end.
  3. Your first flow. One outcome a customer would recognise, owned by a named person, with a measured baseline. Not a process name from the documentation.
  4. Your platform principles. Mine would be four: no agent without an owner, no hop without a gateway, no write without an invariant, no release without an eval.

Exit gate · Accountability, ReturnThe first flow has a named owner and a measured baseline, and risk has agreed the tiers.

Phase 1 · Lay the foundation

Build the layers every agent will share before the first agent goes live: managed model access in approved regions, the AI gateway with token budgets and cost attribution, identity integration so that every agent is a registered identity with an owner, a tool gateway with an internal registry of approved tools, and a trace pipeline that captures every run. If a managed agent runtime fits your cloud, use it rather than building one.

Exit gate · Limits, EvidenceA test agent can call a model and a read-only tool through the gateways, appears in the registry with an identity, and leaves a complete trace.

Phase 2 · Run the first flow, read-only

Put the first flow on the highest rung of the integration ladder available to it. Let the agent prepare and recommend, and let people act. Build the eval set from the first weeks of real traces, with domain experts writing the grading criteria. Publish the agent’s scorecard to the people who use it.

Exit gate · Context, EvidenceThe agent meets its release threshold on real cases and its owner signs off.

Phase 3 · Earn the first write

Before the agent changes anything, add the invariants at the tool layer, human approval for irreversible actions, durable execution with idempotent tools, and a kill switch you have actually tested. Place the flow in its risk tier and produce the evidence that tier needs.

Exit gate · LimitsRollback and the kill switch have been rehearsed, and risk has accepted the evidence.

Phase 4 · Make the second flow cheap

The second flow is the real test. It should reuse the gateways, the registry, the trace pipeline, the eval harness and the skills the first flow produced. Turn what worked into templates and a skills catalogue. Start capturing expert corrections into organisational knowledge, with stewards who decide what is current.

Exit gate · ReturnThe second team ships faster than the first did. If it does not, fix the platform before you add a third.

Phase 5 · Operate at scale

Now the work becomes operations: an agent operations function watching the estate the way a control room watches a grid, cost reported per agent and per outcome, re-certification whenever a model, tool or behaviour changes, the transparency register kept current, and incidents turned into tests. This is the phase most programmes never plan for, and the one that decides whether the platform is still trusted in two years.

One flow through the phases

To make the sequence concrete, take a flow I used in my last essay: checking documents presented under an import letter of credit on the UAE–India corridor. It is built from the public rulebook, not from any institution.

  • Phase 0. The outcome is a client-recognisable one: presented documents checked against the credit before the deadline. A named head of trade operations owns it, and the baseline is how long a check takes today and how often a discrepancy slips through.
  • Phase 1. The agent reaches its model through the gateway, the trade system’s existing API becomes a read-only tool, and the agent is registered with its owner, purpose and autonomy level.
  • Phase 2. The agent compares documents with the credit and drafts a discrepancy note; a checker decides. The eval set comes from past presentations with known outcomes, graded by senior checkers.
  • Phase 3. The first write is deliberately narrow: the agent files its note into the case record, labelled as agent-drafted and on the checker’s behalf. The five-banking-day clock under UCP 600 and any sanctions hold are invariants in code, not lines in a prompt.
  • Phase 4. The second flow, drafting the waiver request to the applicant, reuses the same tools, the same registry pattern and eval harness, and the discrepancy knowledge captured from checkers’ corrections. If it does not arrive faster, the platform needs work before the third.

The team

Whatever the org chart, four jobs have to be done by someone. Owning the shared layers. Sitting with the business to learn how the work is really done; the notes from that work are the most valuable output of the programme, so make capturing them a deliverable. Defining what good looks like and keeping the knowledge current, which usually falls to senior practitioners. And partnering on risk from Phase 0, rather than receiving a finished system in Phase 3.

What to measure

MeasureWhat it tells you
Time from idea to the first flow in productionWhether the platform makes building easy
Time for the second and third flowsWhether the platform compounds or merely accumulates
Cost per completed outcomeWhether the economics work at the level of the task, not the call
Escalations and overrides, and what is captured from eachWhether people trust the agents, and whether the agents are learning
Rollbacks after releaseWhether evaluation is doing its job
Agents with a named owner and a current reviewWhether governance is real or only on paper

Anti-patterns I would refuse

  • An agent with a standing service account and access to everything “for now”.
  • Shared keys between agents, or between an agent and its tools.
  • Invariants that exist only in the system prompt.
  • A memory store with no owner, no expiry and no deletion path.
  • Evaluations that grade only the final answer.
  • One agent bought per function and called a strategy; I made the case against it in Enterprises are organised into functions. Work is not.
  • A platform team that has never shipped a flow on its own platform.
Run CLEAR on anyone who offers to build this for you
  • Context. How will the agent know what this client, this case and this policy require, and who keeps that current?
  • Limits. Who issues the token when one agent calls another, where is each agent’s authority written, and could a prompt get past it?
  • Evidence. Show me the trace of one run, and the evaluation that would have caught its last mistake.
  • Accountability. Who is named as owner, and what happens at the first incident?
  • Return. What will the second flow cost us compared with the first?

If the answers are mostly about the model, keep looking.

The tutorials will keep starting with an API key, and that is fine. They are teaching the part that has become easy.

The hard part was never calling the model. It is the five answers an enterprise owes before an agent acts: whether it understands the job, what it may do, how we will know it worked, who answers for it, and what it returns. Those answers do not come in any box. Decide them before the first agent ships. Afterwards, every one of them is a remediation.
